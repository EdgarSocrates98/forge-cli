        # Grill Gate

- Owner: repo owner. Loop implements; product decisions stay human.
- Problem: directories without `.git` (ZIP download, copied folder, mounted
  volume, network share) are not first-class install targets; the prompt
  requires gitless install for local files already present, WITHOUT
  inventing git operations, downloading, or asking about origin.
- Out of scope: gitless support for REMOTE methods (registry/git/url keep
  requiring git); converting gitless dirs into repos; `--force` bypassing
  manifest/integrity checks (it may re-run the local install, never skip
  validation).
- Review failure: forge-cli treats an intact gitless forge as "not a
  repository"/broken; install silently clones; update runs git pull;
  repair recreates `.git`; uninstall deletes user/manual files; doctor
  reports a gitless dir as unhealthy.
- Riskiest assumption: `forge.json` + manifest validity is enough identity
  to trust a gitless dir — prompt mitigates with INTEGRITY_PARTIAL when
  checksums can't be verified (never UNTRUSTED_SOURCE unless identity is
  contradictory).
- Smallest acceptable: detection + classification + local bootstrap path
  for GITLESS_VALID_FORGE + update-by-file-replacement + receipt fields.

# Context

prompt_evo_install.md FASE 1. The forge-cli currently routes "clone →
install". The target contract (`forge/LocalForgeSourceDetection/v1`)
classifies any user-provided path:

GIT_REPOSITORY | GIT_WORKTREE | GITLESS_VALID_FORGE | GITLESS_PARTIAL_FORGE
| UNKNOWN_DIRECTORY | CONFLICTING_IDENTITY | INVALID_MANIFEST
| UNTRUSTED_SOURCE

Identity levels (prompt): A = `.git` + valid `forge.json`/manifest +
expected structure + verified checksums; B = valid `forge.json`/manifest +
structure + partial checksums; C = `forge.json` only; none = not a forge.
Checksum failure NEVER identifies origin — only lowers trust.

Operation semantics in gitless dirs (explicit contract):
- install → local bootstrap, same receipt shape as any install
- status/doctor → report `is_git: false`, `source_trust`, `manifest_valid`,
  `integrity`
- repair → recreate managed artifacts (runtime/env files) WITHOUT git
  clone/pull/init; manual user files preserved
- update → file replacement/update flow when a newer source is provided
  explicitly; never git pull; never silent download
- uninstall → remove managed artifacts only; never delete the source dir
  contents beyond managed files
- `--force` may re-run local install; it does not skip validation

Failure modes: INVALID_MANIFEST (malformed JSON, missing required fields),
CONFLICTING_IDENTITY (forge.json claims a different forge than structure),
UNKNOWN_DIRECTORY (no forge markers at all) — each with its own error code
(FORGE-SOURCE-GITLESS / FORGE-SOURCE-INVALID / FORGE-SOURCE-NOT-FOUND).

# Acceptance Criteria

- Detection module classifies all 8 states; tested with fixtures for each.
- `forge-cli install <gitless-valid-dir>` performs the local bootstrap and
  writes the same receipt fields as a git install plus `install_method:
  local`, `is_git: false`, `source_trust: <level>`, `manifest_valid`,
  `integrity`, `execution_environment`.
- GITLESS_PARTIAL_FORGE installs only with explicit user confirmation and
  records `integrity: partial`.
- CONFLICTING_IDENTITY / INVALID_MANIFEST refuse with the FORGE-* code and
  actionable guidance (fix manifest / point to correct dir); zero writes
  were performed.
- UNKNOWN_DIRECTORY refuses FORGE-SOURCE-NOT-FOUND.
- repair on gitless dir recreates managed artifacts, runs no git command
  (assert: no `git` spawn), preserves a user-created file planted in the
  dir.
- update on gitless dir: no git pull; with a provided newer path performs
  file replacement; without one refuses with guidance.
- uninstall removes only managed artifacts; planted user file survives.
- doctor lists gitless installs with their trust fields.
- `forge manifest`/status JSON emits the new fields (`is_git`,
  `source_trust`, `integrity`, `execution_environment`) — contract
  documented.

# Constraints

- TypeScript, forge-cli conventions; PT-BR user-facing strings.
- Never convert a gitless dir into a repo; never spawn `git init`.
- No network call on any gitless path (offline guarantee).
- Deterministic classification — same dir → same verdict.

# Review Notes

Reject if: any git invocation on a gitless path, silent trust upgrade,
deleted user files, missing FORGE-* codes, or states collapsible into each
other by malformed input.
