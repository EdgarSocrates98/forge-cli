        # Grill Gate

- Owner: repo owner. Loop implements; product decisions stay human.
- Problem: installers and forge-cli assume `python`/`python3`/`py` on PATH;
  the prompt requires discovering interpreters outside PATH (corporate
  installs, version managers, local dirs) and validating candidates before
  use — a found `python` may be a stub (Windows Store alias), wrong
  version, or non-executable.
- Out of scope: installing Python for the user (FORGE-PYTHON-NOT-FOUND
  points to official/validated sources, never downloads); using
  `python` inside WSL as a native-Windows interpreter; interpreter auto-
  update.
- Review failure: first-found candidate used without validation; Store
  stub accepted as real interpreter; `--python` flag missing; discovery
  order nondeterministic; version check only parses the string instead of
  executing `--version`.
- Riskiest assumption: enumerating candidate locations (registry, known
  dirs, managers) is safe — mitigated by read-only enumeration, timeouts,
  and never executing a discovered binary for anything except the
  documented validation probes.
- Smallest acceptable: priority pipeline + executable validation +
  `--python`/`FORGE_PYTHON` selection + FORGE-PYTHON-* failure taxonomy.

# Context

prompt_evo_install.md FASE 4. Discovery pipeline, in this order
(each step may produce candidates; all validated before use):

1. `FORGE_PYTHON` env var (explicit override)
2. `--python` CLI flag
3. `py` launcher with version spec (`py -3.11`, `py -3`, `py -2`, `py`)
4. `python3`, `python`, `python3.x` on PATH
5. Active venv (`VIRTUAL_ENV`, `.venv`/`venv` in target dir)
6. Version managers: pyenv, uv, conda/mamba, asdf
7. Platform locations: `~/AppData/Local/Programs/Python/*` (Windows),
   `/usr/bin`, `/usr/local/bin`, `/opt/*/bin` (Linux), Homebrew, Windows
   registry uninstall keys
8. Conventional dirs near the repo

Validation per candidate (executable, not string):
- `<exe> --version` runs within timeout → `FORGE-PYTHON-UNEXECUTABLE` if not
- Version satisfies the forge's floor (`requires-python`; ≥3.11 for
  theforge, ≥3.10 for adapters) → `FORGE-PYTHON-INCOMPATIBLE` lists the
  rejected candidates with versions
- Windows Store stub detection (exits 0 but is an App Installer alias):
  detected by path containing `WindowsApps` + probe behavior — treated as
  not-found, reported as such
- Selected interpreter recorded in receipt as `python` object
  `{source, version, executable, selection_reason}`.

Multiple interpreters → deterministic choice (highest compatible version,
explicit selection beats auto); all candidates listed in the discovery
report with per-candidate verdicts.

# Acceptance Criteria

- Discovery function returns ordered candidates with `{executable, source,
  version, valid, verdict}`; fixture tests cover every pipeline stage.
- `--python <path>` and `FORGE_PYTHON` override auto-discovery; explicit
  invalid interpreter errors clearly (not silently falls back to auto).
- Fake stubs (exe that exits nonzero on `--version`; WindowsApps path;
  `python` symlink loop) produce FORGE-PYTHON-UNEXECUTABLE verdicts.
- Version floor enforced via executed `--version`, not path/name parsing;
  FORGE-PYTHON-INCOMPATIBLE output lists every tried candidate + version.
- No candidate → FORGE-PYTHON-NOT-FOUND with platform-appropriate install
  guidance (link to python.org / package manager docs), never a download.
- Receipt/schema gains `python` object; existing installs unaffected.
- Windows tests exercise py-launcher and AppData paths via injected env;
  POSIX tests cover venv/pyenv/uv/asdf/system dirs.

# Constraints

- Read-only filesystem enumeration; no writes during discovery.
- ≤5s timeout per probe, overall discovery budget bounded.
- Offline — discovery never hits the network.

# Review Notes

Reject if: a candidate is executed for anything besides the validation
probes, version floor is string-parsed, Store stubs pass as real,
explicit selection is ignored, or ordering varies between runs.
