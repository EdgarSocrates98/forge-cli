# Context

Current preflight (`runPreflight`) only verifies forge-cli's own needs:
git, Node >= 20, powershell.exe (win32), Python (warn). It runs before any
clone exists, so it cannot see what each project actually requires.

Real declared requirements in `E:\projetos\FORJAS` (verified by inspection):

- `requires-python` in every Python repo's `pyproject.toml`:
  `>=3.10` (spark-forge-aws/azure, platform-forge), `>=3.11` (the-forge,
  forge-doctor-api/data), `>=3.12` (api-forge).
- `forge-portal` needs a working `npm` (`npm ci`, `ng`); its package.json
  declares no `engines`, but custom repos may.
- `requirements-dev.txt` exists in portal — dev-only, out of scope.
- No Java/Docker hard requirements found in setup scripts — out of scope.

# Grill Gate

- Enforcement point: **inside `processRepo` pipeline, after sync** — reads
  each repo's real `pyproject.toml`/`package.json`; failures stay isolated
  per repo. (Not global preflight — repo files don't exist yet.)
- Severity: **`[ERRO]`, skip setup+npm+verify** for that repo — clear
  diagnostic beats a wasted ~40s setup attempt. Batch continues.
- Check set: **all four** — requires-python floor, npm for node repos,
  `pip`/`venv` module availability, package.json `engines` honored.
- Doctor: **extended** — prereq health reported per checkout next to the
  verify result.
- Implementer: Devin.

# Acceptance Criteria

- [ ] `src/prereqs.ts` — `checkRepoPrereqs(repoDir, repo)` returns
      `PrereqCheck[]` (`{ name, ok, detail }`):
  - If `pyproject.toml` exists: parse `requires-python`; compare floor
    against the interpreter resolved by preflight's python resolution
    (same candidates `python`/`python3`/`py`). Fail when unresolved or
    below floor. When no `requires-python` declared, the check is `ok`
    with detail `não declarado` (skip-ish, not a failure).
  - If `pyproject.toml` exists: `python -m pip --version` succeeds AND
    `python -c "import venv"` succeeds (catches missing `python3-venv`
    on POSIX).
  - If `package.json` exists: `npm --version` succeeds.
  - If `package.json` declares `engines.node`/`engines.npm`: resolved
    versions satisfy the ranges (minimal comparator supporting
    `>=`,`>`,`<=`,`<`,`=` and comma-joined parts — enough for floors and
    `>=x,<y` ranges; no full semver dep).
- [ ] `runner.ts` — new phase `phasePrereqs` after configs, before setup
      script. Any `!ok` check → `finish('error', ...)` listing failed
      check names in detail/notes; setup/npm/verify skipped. Checks run
      regardless of `skipScripts` (they're diagnostics, not scripts);
      `--skip-verify` unchanged.
- [ ] `doctor.ts` — `DoctorResult` gains prereq info; any failed prereq
      renders the repo `fail` even if verify passes; `index.ts` doctor
      output shows failed check names compactly; exit 1 unchanged on fail.
- [ ] `plan.ts` — prereq line added to plan output for existing checkouts.
- [ ] `src/ui/strings.ts` — PT-BR strings for the new phase, check names,
      failure detail, doctor prereq summary.
- [ ] Shared helpers: command probe helpers (`commandOutput`/
      `commandWorks`) moved to `utils/system.ts` and reused by preflight +
      prereqs — no duplication.
- [ ] Tests (`tests/prereqs.test.ts` + runner/doctor additions): version
      comparator edges, requires-python parsing, pip/venv/npm check
      branches (execa mocked), prereq failure → repo `[ERRO]` + setup
      skipped, doctor prereq reporting.

# Constraints

- Convention-based, not catalog-hardcoded: checks trigger on file presence
  (`pyproject.toml`, `package.json`), matching the existing design.
- Never silently pass: a requirement that can't be evaluated (python
  unresolved, unparsable floor) counts as `!ok` only when declared and
  unverifiable for the version check; undeclared requirements are `ok`.
- Keep CLI behavior unchanged when all checks pass.
